Start here

The whole engine, explained like you’re five

Imagine a clear desk mat on top of sixteen small sheets of drawing paper. Your fingers move on the clear mat. A helper turns those movements into little drawing instructions, gives each instruction only to the sheets it touches, and keeps tiny “before” photos so Undo can put those pixels back.

1

Fingers make instructions

Splotch does not save “Finger A is at x/y” as the picture. It turns movement into dots and smooth curved path operations.

2

Small canvases do the painting

The big visible area is split into sixteen ink tiles. A curve crossing four tiles paints four small surfaces, not one giant iPad-sized surface.

3

Undo keeps “before” pieces

Before a command changes a tile, the engine copies it. At commit it crops that copy to just the dirty rectangle. Undo pastes those pixels back.

Input: a contact stream begins. The transparent full-size canvas receives pointer events, captures the pointer, and maps screen coordinates back into the drawing’s permanent paper coordinates.

How raw motion becomes a smooth line

The browser often delivers one pointermove per display frame, but includes intermediate samples through getCoalescedEvents(). Splotch consumes all of them. For each raw point, it draws a quadratic curve from the previous midpoint to the new midpoint, using the previous raw point as the control point. Adjacent curves share a tangent, so corners look smooth without a heavy fitting algorithm.

Coalesced samples

Replays the browser’s hidden in-between points so fast scribbles do not collapse into long straight chords.

Pointer capture

Keeps a stroke flowing across floating buttons and canvas edges instead of ending when hit testing changes.

Edge-swipe classifier

Buffers touch starts in OS gesture bands, then discards inward swipes or commits cross-edge/tap motion as ink.

Resume detector

A gap over 100 ms plus a jump over 10% of the paper’s short side becomes a new contact, avoiding a stray bridge line.

Pen-stream repair

Adopts WebKit Apple Pencil contact streams that arrive as moves with no new pointerdown after a fast UI tap.

Speed window

A 100 ms sliding distance window drives pencil-scratch audio volume without reacting to every tiny jitter.

Style is captured per pointer. Color, width, eraser, Magic, crayon, and crayon seed are copied into PointerState when that contact begins. Later UI changes do not rewrite already-emitted operations.

Deep dive 2

Why the paper is tiled

On a large iPad, JavaScript could finish drawing quickly and still leave WebKit hundreds of milliseconds behind while it flushed one huge mutated canvas to the display. The decisive variable was the maximum size of one active surface—not the total painted pixel count. Sixteen smaller canvases kept the same full resolution while removing the presentation starvation.

Cull first, paint second

Dots and paths carry paper-space geometry. The renderer finds a conservative box around the start, control points, and endpoints, expands it by half the stroke width plus a 2 px anti-alias bleed, and tests that box against each tile’s paper bounds.

Only intersecting tiles allocate backing stores, capture undo state, become visible, and run renderOp(). Tile transforms subtract the tile’s x/y origin, so operations remain in one global paper coordinate system.

🧱 Live ink tiles

  • Attached to the page and physically presented.
  • Hidden whenever they contain no visible ink.
  • Crayon preview backings allocate only when touched.
  • CSS positions snap boundaries to device pixels.

🗄️ History-base tiles

  • Offscreen raster storage for old, non-undoable commands.
  • Created only when folding starts.
  • Track a painted bit so blank bases do not blit.
  • Use the same 4×4 paper topology.
Measured reason, not aesthetic preference. The original full-resolution iPad surface showed roughly 417 ms of render starvation per drawing-second and paint P95 around 480 ms. The tiled vector-history prototype measured zero starvation and roughly one-refresh paint latency. Tiling changes topology, not resolution.

Deep dive 3

The undo lifecycle: vectors on top, pixels underneath

Production undo is a hybrid. Recent commands remain as vector operations and own cropped pixel patches of what was underneath them. Old commands lose undo patches, then fold into a tiled raster base after the child stops drawing.

The small counts above are illustrative. The normal product cap is 20 undoable commands.

Begin

The first pixel of the whole multi-finger group records whether the canvas was empty and opens one active command.

First tile mutation

Copy that tile once, then union every operation’s transformed dirty bounds into the command’s rectangle.

Commit

Crop each temporary tile copy to its dirty rectangle; push the command; retain up to 20 steps.

Budget

If patches exceed six aggregate papers of RGBA bytes, drop the oldest patches but keep at least the newest two.

Wait

Pointerdown cancels compaction. After 1.5 seconds without input, one non-undoable command may fold.

Fold

Replay that command through the same renderer into the offscreen 4×4 raster base, then discard its vector entry.

Undo

Pop the newest command; clear only its dirty patch rectangles and blit the saved “before” pixels back.

Fallback

If tile geometry changed or another finger is live, replay history so in-flight pixels and patch pre-state remain correct.

ordinary tiled undoidentity-space patch restore
tile.ctx.save();
tile.ctx.setTransform(1, 0, 0, 1, 0, 0);
tile.ctx.clearRect(patch.x, patch.y, patch.width, patch.height);
tile.ctx.drawImage(patch.canvas, patch.x, patch.y); // the restoring BLIT
tile.ctx.restore();

Clear is one command, but it is spread across frames

Clearing several full tiles and snapshotting them synchronously caused long iPad frames. The current clear hides affected tiles immediately, then captures at most one visible tile per animation frame. Each backing is physically cleared two presented frames later. An immediate Undo either restores completed patches or simply unhides still-preserved backings.

Why patches, not replay, for ordinary Undo? Replaying twenty commands across sixteen tiles reached roughly 1.8 seconds on the physical iPad. Cropped dirty patches brought the engine portion of a normal undo to about 0–1 ms while keeping live drawing fast.

Deep dive 4

Rasterization, vectors, and what “BLIT” means

BLIT

Pronounced like “blit.”

A fast rectangle-shaped pixel copy.

The name comes from “bit block transfer.” In this Canvas 2D engine, a BLIT is usually a drawImage(sourceCanvas, …) call that copies already-rasterized pixels from one canvas or bitmap into another. It does not re-run curve geometry or brush math.

Source pixel rectangle
→
Destination receives the same pixels
Vector does not mean “never rasterized.” Recent history stores semantic operations such as “quadratic path, 18 px wide, blue.” The moment renderOp() paints that operation onto a canvas, the browser rasterizes it into RGBA pixels. Splotch deliberately keeps both forms at different stages.

Four operation kinds drive the production tiled stream

dot

A filled circle at contact start, carrying color, radius, and brush flags.

path

A start point plus midpoint-smoothed quadratic segments, width, pointer id, and brush flags.

crayonFlush

Stamp each dirty crayon pass buffer into its normal tile, then hide and clear the preview planes.

clear

Reset crayon state and clear the target in device space.

The union also contains crayonPassRaster, but the production tiled renderer records raw crayon ops plus flushes. The raster-op path belongs to the retained legacy /dev/engine renderer and its white-box history coverage.

Deep dive 5

One geometry pipeline, four paint personalities

Every brush produces the same dot/path geometry. The flags on the operation decide how renderOp() turns that shape into pixels.

🖊️

Pen

Solid color, source-over. It is the simplest route: stroke or fill the shape directly.

⌫

Eraser

Opaque shape with destination-out. Alpha is removed, so paper underneath becomes visible.

🪄

Magic

Fills the same shape with a no-repeat pattern from a coloring fill or held random rainbow.

🖍️

Crayon

Two density passes of deterministic paper tooth, accumulated and mixed once per deposition pass.

Magic brush: paint through an immutable color sheet

A coloring-page fill—or a generated rainbow on blank paper—is contain-fitted into the engine’s paper space. When the platform supports it, a worker fetches, decodes, rasterizes, and transfers an ImageBitmap. Each tile crops its own pattern source so WebKit never samples one giant full-page pattern during live drawing.

The first time a Magic operation paints, it captures the current sheet snapshot on that operation. Removing or swapping the coloring page recodes retained Magic ops to the new page’s sheet as one undoable command; a theme change recodes them in place without adding an undo step. An operation created before an asynchronous sheet is ready initially paints nothing; one gated repaint resolves it when the sheet arrives.

Why crayon uses two BLITs

Dozens of path ops overlap inside one gesture. Mixing each op with the paper underneath would compound repeatedly. Instead, the entire deposition pass accumulates at full opacity on preview buffers, then mixes exactly once:

The nice fixed point: min(c, c) = c. Red crayon over red crayon can fill different tooth pits without progressively darkening the red. Different colors still mix subtractively.

Crayon’s other algorithms

N

Tileable value noise

Four wrapped octaves build a deterministic 256×256 height field from fixed-seed Mulberry32 random numbers.

0/1

Binary alpha + ordered dither

Every wax texel is fully opaque or fully clear, keeping repeated overlapping ops pixel-stable during replay.

↩

Pass splitting

A turn sharper than 100° or re-entry near older ink starts a new seed phase, so back-and-forth scribbles build up without lifting.

64

Checkpoint flush

A very long pass stamps every 64 path ops so a tile-local preview buffer never accumulates compositor-sized dirty work.

2ms

Frame-budgeted warmup

New color texture tiles build in row chunks with a two-millisecond frame deadline; synchronous build remains the correctness fallback.

LRU

Bounded pattern cache

Recently used color/pass canvases stay cached; old custom colors evict so detached canvas memory cannot grow forever.

Deep dive 6

Coordinate spaces, sharpness, and rotation

Operations are never tied to the current phone orientation. They live in “paper space,” a stable pixel coordinate system adopted from the viewport. The screen is just a view onto that paper.

The paper locks when it has ink

On a blank canvas, a resize adopts the new viewport. With ink, a real orientation change keeps the old paper dimensions. The paper sheet, coloring overlay, and entire live tile wrapper receive one CSS contain-fit-and-center matrix. Pointer input runs through the inverse matrix.

No tile is resized, no settled ink is replayed, and returning to the original orientation reveals the exact original pixels. In tiled production, contacts that begin in the temporary letterbox margin are ignored because that margin is not paper.

Why CSS? Resizing 48 possible live canvases on rotation could produce 56–57 ms physical-iPad frames. Presenting the existing paper-sized pixels with one CSS transform reduced the measured maximum to roughly 20–31 ms.

Live resolution

  • renderScale = min(devicePixelRatio, 2)
  • Fixed for the engine session.
  • Stroke widths begin as CSS pixels, then scale once.
  • Tiling preserves this resolution.

Export resolution

  • exportScale = max(devicePixelRatio, 2)
  • Independent from the live scale cap.
  • Matched 2× exports reuse settled live tiles.
  • Mismatched scales replay vectors at export scale.

The engine boots before Svelte hydration

The home page is prerendered. As soon as the engine module evaluates, it finds the existing #drawingCanvas and initializes pointer handling. Later, DrawingCanvas.svelte adopts that running singleton, attaches callbacks, and pushes reactive color/tool state. This avoids a several-hundred-millisecond “canvas looks ready but cannot draw yet” window.

export async function exportCanvasBlob(...) {
  const scale = currentExportScale();

  // Must happen before loading the save-time module.
  const snapshot = snapshotStrokes(scale);

  const { composeExportPng } = await import('./exportDrawing');
  return composeExportPng(snapshot, scale, overlayImage, options);
}

That snapshot-before-await ordering protects save-on-delete: a caller can start an export and immediately clear the live engine without blanking the saved image. The export module and texture are warmed at idle but remain out of the startup preload graph.

Fast path

  • No active pointers.
  • Live and export scales match.
  • createImageBitmap, Worker, and OffscreenCanvas exist.
  • Only the worker owns a full-page canvas.

Compatibility path

  • Active stroke, scale mismatch, or missing APIs.
  • Replay raster base + retained commands into an export surface.
  • Worker encoding when possible; main-thread encoding fallback.
  • Same shared compositor rules.

Learned the hard way: platform facts you cannot see from a laptop

2.3M

The canvas flush cliff

On the target iPad, mutating one large canvas starved rendering; the surface-size cliff was bounded between roughly 1.6 and 2.3 megapixels per surface for that device and workload — an observed bound, not a universal WebKit constant. Sixteen tiles sit well below it. Thirty-two lost separately, to over-tiling costs: more canvases, more target visits, more seams.

163

toBlob blocks WebKit

The spec says encode “in parallel”; WebKit encodes 163–206 ms on the main thread. Deferring those encodes cut a 2,390 ms stroke-end freeze to 1 ms — the experiment that convinced today’s tiled undo to never encode at all: over budget, it evicts the oldest patches instead.

60

Safari’s hidden Hz cap

requestAnimationFrame runs at 60 Hz on a 120 Hz ProMotion iPad, so the real frame budget is 16.7 ms, not 8.3 — discovered only by scoring a capture of the actual screen.

GPU

The desynchronized trap

The low-latency canvas hint passed every headless gate at 59.5 FPS — then rendered the canvas opaque black on a real Android WebView, because a hardware overlay plane does not alpha-composite with the DOM stacked beneath it.

200×

Never read a big canvas per op

drawImage from a large freshly painted canvas forces a full source-surface snapshot — measured at ~200× the cost of a pattern fill under software rendering. Composite small layers onto big surfaces, never the reverse.

The graveyard: working code, killed by a number

†
Command-replay undo

Beautiful in June: kilobytes of history, 0.1 ms undos. Dead in July: the first textured brush broke the bit-identical-replay contract, and crayon commits hitched 1,171–2,222 ms. Byte-exact snapshots won; only the byte budget survived.

†
Web-font preload

Mechanically worked — font fetch 1,950 → 911 ms — and still lost: it consistently cost ~140 ms of LCP on a route that paints no text, by stealing bandwidth from the paper texture.

†
Baked paper-grain tiles

A finished, green implementation measured 0.49 → 0.50 ms (light) and 0.58 → 0.53 ms (dark) — a null result with a sign disagreement. ~350 working lines closed unmerged, with a post-mortem of how the original sweep fooled itself.

†
Per-stroke crayon isolation

Prototyped so a textured stroke could composite once and stay bit-identical while command-replay undo simplified and re-chunked its operations — which would have permitted soft fractional-alpha tooth: ~6× worse draw and ~100× worse undo. Rejected in the same PR that measured it.

†
Blob-resize save preview

Three candidates raced on device for the polaroid thumbnail: decode-and-resize the finished PNG lost at 49 ms; downscaling the export worker’s own composition won at 24 ms.

The method is the moral: no emulator or headless gate reproduced the iPad stall — synthetic gates passed while the real screen visibly froze. Every fix on this page was a single-variable trial on the physical device (forty-four for the tile grid alone, each backed out before the next), driven by trusted XCUITest touch at 100–170 moves per second and scored from a capture of the screen itself.

What else is hiding in here?

The supporting algorithms worth knowing

AABB

Conservative bounds

Control-point hull + half stroke width + 2 px AA bleed drives tile culling, crayon dirty bounds, and undo patch crops.

¼

Downscaled empty scan

Each tile is copied to a 0.25× CPU scratch canvas and alpha-scanned there, avoiding readback flags on GPU drawing surfaces.

fit

Contain-fit transform

min(boxW/paperW, boxH/paperH), then center. The same matrix presents paper and inversely maps input.

rAF

Progressive scheduling

Clear capture, hidden tile migration, and crayon warming split work across animation frames so no one flush monopolizes a frame.

LIFO

Patch correctness

Undo only restores the newest command. Last-in-first-out ordering guarantees untouched pixels already match the command’s pre-state.

W

Worker ownership

Magic-sheet rasterization and full-page PNG composition transfer bitmaps across threads instead of allocating giant UI-thread surfaces.

1×

Single-replay recovery

A lost worker canvas context gets exactly one full replay from inputs retained in the worker — restored state is never trusted — then a stable failure code retires it.

Not currently Ramer–Douglas–Peucker. Older ADRs describe a replay-era stroke simplifier, but that architecture was superseded. The production tiled tail retains operations at their emitted render granularity; exact geometry also keeps crayon flush ordering and binary texture stable.

Keep beside the code

Jargon decoder

Anti-aliasing (AA)
Partly transparent edge pixels that make a curve look smooth instead of stair-stepped.
Backing store
The real bitmap dimensions of a canvas, distinct from its CSS width and height on screen.
BLIT
A rectangular copy of already-rasterized pixels, usually implemented here with drawImage.
Command
One undoable group of operations—normally every finger whose contact overlaps in time.
Compositing
The rule for combining new pixels with old ones: source-over, destination-out, darken, and alpha.
Culling
Skipping tiles whose bounds cannot intersect an operation.
Dirty rectangle
The smallest conservative pixel box a command may have changed.
DPR
Device pixel ratio: how many physical display pixels correspond to one CSS pixel.
Fold / compact
Rasterize an old, non-undoable vector command into the tiled history base.
ImageBitmap
A transferable decoded bitmap used to hand tile or Magic-sheet pixels to a worker efficiently.
Operation (op)
A render instruction such as dot, quadratic path, crayon flush, or clear.
Paper space
The stable coordinate system in which operations, Magic sheets, and history live.
Patch
A cropped pre-command pixel snapshot used to reverse the newest command.
Raster
A grid of RGBA pixels. Canvas backing stores, patches, history bases, and PNGs are rasters.
Source-over
Normal painting: place the source over the destination using source alpha.
Destination-out
Eraser compositing: source alpha removes destination alpha.
Tile
One cell in the 4×4 live or history surface grid.
Vector
Semantic geometry and paint data that can be rendered again at a chosen scale.

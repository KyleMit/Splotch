The undo button isn't broken.
WKWebView is lying about where you tapped.

Issue 1194 was filed as "undo doesn't restore the drawing after a blank rotation." It is actually a 32-pixel disagreement between two coordinate systems inside the iOS WebView — and it silently kills every toolbar button in portrait, not just undo.

What actually happens

Three answers to "where did the finger land?" — and they disagree

One trusted touch on the undo button, after rotating the blank canvas from landscape to portrait. The touch events, the pointer events, and the synthesized click each report a different Y coordinate for the same physical contact. Drawn to scale from the measured values:

The raw measurement

Event clientY pageY Dispatch target elementFromPoint(clientY)
touchstart / touchend 778 746 undoButton undoButton ✓
pointerdown / pointerup 746 746 undoButton .actions-panel ✗
click (synthesized) 737 737 .drawer-toggle .drawer-toggle ✗

There is no correct accessor to reach for: clientY, pageY, screenY and offsetY on the pointer event all carry the same skew. The only skew-free signal the browser gives us is e.target.

Where it breaks in our code

We throw away the right answer and recompute a wrong one

scribbleTap — the action every toolbar button activates through — doesn't trust the target the browser dispatched to. It re-derives one from the coordinates: 

// web/src/lib/actions/scribbleGuard.ts
function eventHitsControl(e: PointerEvent): boolean {
  const hit = node.ownerDocument.elementFromPoint(e.clientX, e.clientY);  // ← 746, not 778
  return node.contains(hit);                                     //   → false
}

function move(e) { /* … */ if (moved > 8px && !eventHitsControl(e)) press.dragged = true; }
function up(e)   { finishPress(!press.dragged && eventHitsControl(e)); }  // → never activates

Note it is called twice: once in up() to decide the release landed on the control, and once in move() to decide the press became a drag. That second call is what makes this subtle — and it is where one of the four fixes falls down.

The four options

All four were built, unit-tested, and driven on a real device

Each is a branch off main. Each passed the full 2,050-test unit suite and svelte-check. Each was then built into the native app and driven with trusted XCUITest touch through four on-device scenarios.

Option 1

Trust the dispatch target

In up(), accept the press when e.target is inside the control, before falling back to the hit test. The browser already told us; stop second-guessing it.

Why option 1 fails the wiggle tap

It only patches up(). By the time up() runs, move() has already seen 12px of travel, asked eventHitsControl() whether the finger is still on the button, been told no (from the same 32px-wrong coordinates), and latched dragged = true. The press is dead before the fix gets a vote.

This is the failure mode worth dwelling on: option 1 is the smallest diff, passes the bug as filed, and would have looked completely fixed in review. It took writing a scenario the issue never described to catch it.

Recommendation

Option 4 — delete the cause, not the symptom

What changes

// capacitor.config.json
  "ios": {
-   "contentInset": "always"
+   "contentInset": "never"
  }
  • It fixes everything downstream at once. Not just scribbleTap — every control, every gesture, and any future code that trusts pointer coordinates. Options 2 and 3 leave the platform lying to us and correct the lie at one call site.
  • Zero runtime cost, one line of diff. Option 3 works, but installs a window-level touchmove listener that fires on every move of every stroke — the exact thing our own hot-path rule forbids, in an app whose whole story is stroke latency.
  • It lands a feature we already built. The Notch Band now paints on iOS. ADR-0026 designed it, shipped it on Android, and named ios.contentInset as the reason it never worked here — "revisit capacitor.config.json ios.contentInset if the band doesn't extend under the notch."

Two things to weigh before merging

It is a visible change. Every edge-anchored element's relationship to the top of the screen shifts, and the status bar becomes ink-coloured. I verified that on the iPad mini simulator in both orientations only — it wants a look on a physical iPad and an iPhone, both themes, before it ships.

It is specific to this source of skew. If iPadOS windowing later introduces another coordinate mismatch, option 2 would still hold where option 4 wouldn't. If the visual change isn't wanted, option 2 is the runner-up and is purely internal.

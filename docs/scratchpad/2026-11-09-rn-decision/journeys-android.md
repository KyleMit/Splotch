157). Arms: RN = `art.splotch.app.dev` (installed **perf-probe** Release, `427756f14`, APK sha256

`art.splotch.app.baseline.main` (Release, `ef3d1eb20`). J25 swapped in the plain RN Release and

Method: `adb shell input` for taps and swipes, `adb shell input motionevent` for held contacts, and
my own Appium 3.6 + UiAutomator2 8.2.2 server (W3C multi-pointer actions, page source with
`waitForIdleTimeout=0`) for multi-touch and for finding controls by their accessibility labels.

are in the campaign scratch folder under `journeys-android/` (`bin/`, `raw/`, `logs/`). Screens are
in `shots/galaxy/<arm>/`, with identical slugs in both arms.

## Feature parity (from both `docs/ARCHITECTURE.md` UI glossaries)

The control sets are the same in both arms: palette, Custom Color picker, Clear drag, Actions Panel
(Pen, Crayon, Magic brush, Eraser, Undo, Screenshot, Stroke width, Coloring books, AI), 8 coloring

a gallery or stickers.** I added four extras: J-x1 Android Back, J-x2 Custom Color, J-x3 Stroke
width and J-x4 Auto-Save on Delete.

## Accessibility (J19, and the orchestrator's `uiautomator dump` question)

* **The RN tree is present and labelled.** Plain `uiautomator dump` failed on RN with "null root
  node returned by UiTestAutomationBridge" at 23:31 and twice at 00:45, while shipping dumped fine
  at 00:45. After that it succeeded 7 of 7 times (00:49–00:53: cold launch +3 s and +10 s, after a
  stroke, with Settings open and closed), every time with every control named (`raw/rn_uia_ok.xml`).
  The failure is intermittent. Its likely cause is another UiAutomation client (UiAutomator2 is
  single-client) or a client that had only just closed, not missing labels. Across the whole
  session, UiAutomator2 page source, which reads the same `AccessibilityNodeInfo` tree TalkBack
  does, returned the full labelled RN tree on every query. `dumpsys accessibility` shows RN's window
  as an active, focused `TYPE_APPLICATION` (`logs/dumpsys-a11y-rn.txt`).
* **TalkBack traversal: not driven** (2 attempts). Injected swipes and taps bypass touch
  exploration, and Alt+Right did not move focus. UiAutomator2 also suppresses TalkBack unless
  `disableSuppressAccessibilityService` is set. TalkBack was on from 00:45 to 00:50. Its own "Allow
  phone access?" prompt was cancelled 3 times. The prior settings were restored exactly.
* **Shipping gaps in the tree, unconfirmed for TalkBack.** The Brush Menu and Stroke Width options
  appear as `ToggleButton`s with **no name** (source has `aria-label`; both uiautomator paths
  agree). Hub switches and radio buttons expose no checked state, and section switches expose it
  only sometimes. That fits WebView's reduced accessibility mode for non-screen-reader clients, so a
  real TalkBack pass is needed. RN names every option but does not expose the selected brush or
  size.
* **No unlabelled clickable** in either arm across all captured screens. Colour hexagons are
  labelled by hex code in both arms (for example "#2ECC71").
* **200% font scale.** Both arms stay usable with no overlapping chrome. Shipping clips one title
  (D4). RN visibly scales headings less.
* **Side effect to know.** While any UiAutomator2 session is open it suppresses the phone's other
  accessibility service (`nu.nav.bar` navigation bar). It rebinds when the session ends; I closed
  mine at every lock release.

## J25 dense history (200 strokes, ~10 min, Sound on, then 20 Undos)

Held both `dev-galaxy` and `rig` locks. RN ran the **plain** Release (`371533dd…`, swapped in, then
the probe `7e6af612…` restored and checked by sha256). Each arm got a cold launch, Pen, a cycle of 4
colours, 200 random 150–400 ms strokes at one per 3 s, then 20 Undos 0.4 s apart (`bin/dense.py`).
Next came 3 cycles of 20 strokes + 20 Undos (`bin/cycles.py`), then 20 s idle. Shipping PSS = app
plus its WebView renderer (as in the perf lane).

* Both apps stayed responsive. A probe stroke after the Undos inked in both, and nothing crashed.
  Both cap Undo at 20 (`MAX_UNDO_DEPTH = 20` in both trees).
* **RN's Undo path costs memory and frames.** The first 20-Undo burst added +72 MB, almost all
  native heap. Identical draw/undo cycles kept climbing (+20–30 MB a cycle, partly reclaimed at
  idle). Over the session RN grew +138 MB against shipping's +36 MB (3.8×), ending at 413 MB against
  314 MB (1.32×). That trips the perf lane's pre-registered "growth across the session ≥2×
  shipping's" memory rule. The Undo burst misses half its 120 Hz frame deadlines, but no frame
  reaches 50 ms, so it is not a ">100 ms core-action stall". Severity: **minor**, with the memory
  climb worth a longer leak check. The perf lane owns the memory verdict.

## Could anything here flip the decision?

Unlikely on its own. Every core journey ties on the Galaxy, including palm, multi-finger and
held-contact behaviour, which match pixel for pixel. RN has one repeatable ink-loss defect (D1),
behind an opt-in setting and probably a small fix. It also has an Undo memory climb (D7) that trips
the perf lane's growth rule without visible harm. Shipping has three minor defects (D2–D4). Whether
D1 counts as a "repeatable RN contact-loss" non-compensable failure, and how D7 scores, is the
orchestrator's call. Neither difference makes RN clearly better on the Galaxy.

    "body": "Related: #3084 (the CI-builder idea, deferred). Part of #2978.\n\n## What\n\nDevice checks of JS-only fixes should not need a native rebuild. Today every fix gets a full Release `assembleRelease` or `xcodebuild`, which takes 3–5 minutes and saturates the Mac, even when only TS/TSX changed. On 2026-10-20 most diagnose-and-verify loops for #3062 to #3071 were native rebuilds of unchanged native code.\n\n## How\n\n1. **Debug probe plus Metro (functional checks).** Build a Debug probe once per device, with a suffixed bundle ID under the allowed `art.splotch.migration.probe*` set. After that, a JS change is a reload:\n   * Run Metro on a free port (`npm --silent run show:free-port`).\n   * On Android, use `adb reverse`; the iPad reaches Metro over the LAN.\n   * Debug JS is slower, so this is for \"does it draw / is it visible / does the tap land\", not timing.\n2. **Release with a swapped JS bundle (timing-faithful).** Build the Release probe once, then on each change only regenerate the bundle (`react-native bundle`, about 30–60 s) and load it without a native build. Two candidate routes:\n   * repackage and re-sign the APK, and for iOS replace `main.jsbundle` in the `.app` and re-sign;\n   * a probe-only switch that loads a sideloaded bundle path. It must be absent from shipping builds and drift-guarded like the other probe flags.\n3. **Document the split** in `docs/MOBILE/` and the device-parity tooling: JS-only changes use route 1 or 2; native (Kotlin/Swift) changes and performance captures use a full local build.\n\n## Done when\n\n* A JS-only fix can be verified on the Galaxy and the iPad without running Gradle or xcodebuild after the first build.\n* The Release swapped-bundle route reproduces the same behaviour as a full Release build on one known fix (for example #3071's swatch probe).\n* The workflow is documented where the device skills point.",
